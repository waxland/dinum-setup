## 🔑 2. L'API Légifrance sur le Portail PISTE

La **Direction de l'information légale et administrative (DILA)** expose l'ensemble des données juridiques françaises via des APIs REST hébergées sur **PISTE** (_Plateforme d'Intermédiation des Services pour la Transformation de l'État_).

### A. Protocole d'Authentification OAuth2
L'accès à l'API requiert une authentification **Client Credentials Flow** :

```http
POST https://oauth.piste.gouv.fr/api/oauth/token
Content-Type: application/x-www-form-urlencoded

grant_type=client_credentials&client_id=VOTRE_CLIENT_ID&client_secret=VOTRE_CLIENT_SECRET&scope=openid
```

Le serveur renvoie un `access_token` JWT avec une durée de validité (généralement 1 heure).

### B. Principaux Endpoints Utilisés

| Endpoint PISTE / DILA | Méthode | Rôle & Usage |
| :--- | :--- | :--- |
| `/dila/legifrance/lf-engine-app/consult/code` | `POST` | Récupère la table des matières ou l'arborescence d'un code (ex: Code de la commande publique). |
| `/dila/legifrance/lf-engine-app/consult/getArticle` | `POST` | Récupère le texte intégral d'un article par son identifiant univoque (`LEGIARTI...`). |
| `/dila/legifrance/lf-engine-app/search` | `POST` | Moteur de recherche multicritères (par mots-clés, numéros d'articles, dates d'effet). |
| `/dila/legifrance/lf-engine-app/suggest` | `POST` | Autocomplétion dynamique pour assister la saisie dans le formulaire de recherche. |

## ⚡ 3. Pourquoi un Proxy Django & un Cache Redis ?

Pour des raisons d'architecture, **le frontend Docs ne contacte jamais l'API PISTE directement** :

1. **Sécurité des Secrets :** Les clés d'API `CLIENT_ID` et `CLIENT_SECRET` restent strictement confinées sur le serveur backend Django.
2. **Gestion des Quotas & Rate-Limiting :** PISTE applique des limites de requêtes par seconde. Le proxy mutualise les requêtes pour l'ensemble des agents.
3. **Mise en Cache Haute Performance (Redis) :** Les textes de lois consolidés ne changent pas d'une seconde à l'autre. Une mise en cache avec un **TTL de 24 heures** permet de servir 95% des requêtes en moins de **10 millisecondes**.
4. **Normalisation des Réponses :** Le schéma de réponse brut de l'API DILA est particulièrement verbeux. Le proxy Django extrait uniquement les champs nécessaires au frontend pour alléger la charge réseau.

## 🤝 4. Modélisation CRDT dans l'Éditeur (Yjs)

L'éditeur Docs s'appuie sur le framework **BlockNote**, lui-même construit sur **ProseMirror** et **Yjs**.

Lorsqu'un bloc `/loi` est inséré par un utilisateur, ses données sont modélisées sous forme de propriétés immuables au sein d'un nœud `Y.XmlElement` :

```typescript
// Structure de données CRDT répliquée entre tous les pairs
export interface LawBlockProps {
  codeId: string;           // ex: "LEGITEXT000037701460"
  codeTitle: string;        // ex: "Code de la commande publique"
  articleNumber: string;    // ex: "Article L. 2122-1"
  articleId: string;        // ex: "LEGIARTI000037728472"
  content: string;          // Texte intégral certifié de l'article
  status: "in_force" | "amended" | "abrogated" | "future";
  versionDate: string;      // Date de consolidation (ex: "2026-09-14")
  legifranceUrl: string;    // URL officielle vers le permalien Légifrance
  hashVerification: string; // Empreinte SHA-256 pour vérifier l'intégrité
}
```

### Mécanisme de Réconciliation
Si deux utilisateurs ouvrent le même document :
1. L'utilisateur A insère l'article via `/loi`.
2. Yjs génère un ensemble d'updates binaires (`Uint8Array`) transmis par WebSocket.
3. L'utilisateur B voit le bloc s'afficher en temps réel sur son écran, avec le rendu stylisé DSFR et les liens cliquables.
4. Aucun conflit d'édition de texte interne n'est possible : le bloc est traité comme une entité atomique certifiée.
