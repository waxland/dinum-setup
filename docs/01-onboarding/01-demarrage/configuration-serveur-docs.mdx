Ce tutoriel récapitule les fichiers à connaître lorsque **La Suite Docs** est configurée sur un serveur de développement ou une machine distante.

> ⚠️ Ce guide distingue volontairement les fichiers versionnés du dépôt et les fichiers locaux propres au serveur. Les valeurs sensibles ne doivent jamais être ajoutées à Git.

> ⚠️ **Point d'attention important :** si vous ne pouvez pas modifier directement le projet `src/docs`, faites toute la configuration depuis ce dépôt `dinum-setup` avec les fichiers locaux et les variables Docker décrits ci-dessous. Ne modifiez pas les fichiers générés ou les dépendances du projet Docs pour corriger une URL serveur.

---

## 1. Les fichiers à connaître

| Fichier | Où le trouver ou le créer | Rôle |
| :--- | :--- | :--- |
| `next.config.js` | `src/docs/src/frontend/apps/impress/next.config.js` | Configuration de construction et de développement Next.js. |
| `.env.local` | `src/docs/src/frontend/apps/impress/.env.local` | Variables d'environnement propres à la machine ou au serveur. Ce fichier reste local. |
| `common.local` | `src/docs/env.d/development/common.local` | Surcharges locales du backend Docker Docs : URLs publiques, OIDC, collaboration et services. |
| `kc_auth.local` | `src/docs/env.d/development/kc_auth.local` | Hostname public généré par Keycloak pour éviter les redirections vers `localhost`. |

Dans le dépôt actuel, l'option s'appelle **`allowedDevOrigins`**. Ce n'est pas `allowDevOrigin` : le nom est au pluriel, car plusieurs origines peuvent être autorisées.

---

## 2. `allowedDevOrigins` : autoriser l'origine du serveur

Dans `next.config.js`, la configuration actuelle contient :

```js
const nextConfig = {
  allowedDevOrigins: ["docs.127.0.0.1.nip.io", "207.175.155.66"],
  output: "export",
  trailingSlash: true,
};
```

Cette option indique à Next.js quelles origines peuvent accéder au serveur de développement. Elle est utile lorsque l'application est ouverte depuis :

- un nom de domaine local, ici `docs.127.0.0.1.nip.io` ;
- l'adresse IP publique ou privée du serveur, ici `207.175.155.66`.

### Ajouter une nouvelle origine

Si le serveur est accessible avec un autre nom de domaine, ajoutez uniquement ce domaine dans la liste :

```js
allowedDevOrigins: [
  "docs.127.0.0.1.nip.io",
  "207.175.155.66",
  "docs.example.gouv.fr",
],
```

Utilisez l'origine réellement utilisée dans le navigateur. N'ajoutez pas `http://`, `https://`, un chemin ou un slash final dans cette liste :

```text
✅ docs.example.gouv.fr
❌ https://docs.example.gouv.fr/docs
❌ docs.example.gouv.fr/
```

Après toute modification de `next.config.js`, redémarrez le serveur Next.js :

```bash
cd src/docs/src/frontend/apps/impress
pnpm dev
```

> Cette option concerne surtout le serveur de développement. Elle ne remplace pas la configuration du reverse proxy, du DNS, du TLS ou des règles de pare-feu en production.

## 3. `.env.local` : les variables propres au serveur

Le fichier `.env.local` permet de définir les valeurs qui changent selon l'environnement : URL de l'API, adresse du serveur, activation d'une fonctionnalité ou identifiants non publics.

Créez-le dans le dossier de l'application Next.js :

```bash
cd src/docs/src/frontend/apps/impress
touch .env.local
chmod 600 .env.local
```

Exemple de structure, à adapter aux variables réellement attendues par l'application :

```dotenv
# URL publique de l'API Docs utilisée par le navigateur
NEXT_PUBLIC_API_ORIGIN=http://207.175.155.66:8071

# Désactiver le service worker uniquement pour diagnostiquer un environnement local
NEXT_PUBLIC_SW_DEACTIVATED=false
```

### Règles importantes

- Les variables préfixées par `NEXT_PUBLIC_` peuvent être exposées au navigateur. N'y placez jamais de mot de passe, de clé privée ou de jeton.
- Les secrets sans préfixe `NEXT_PUBLIC_` restent destinés au serveur, mais leur traitement dépend du code qui les lit.
- Ne copiez pas de vraies valeurs sensibles dans la documentation ou dans un fichier `.env.example` public.
- Vérifiez que `.env.local` est ignoré par Git avant d'y mettre une valeur privée :

```bash
git check-ignore -v src/docs/src/frontend/apps/impress/.env.local
```

Si Git ne retourne aucune règle, ajoutez l'entrée appropriée au `.gitignore` avant de continuer :

```gitignore
.env.local
.env.*.local
```

## 4. `common.local` : la configuration Docker du backend Docs

`common.local` est différent de `.env.local` :

- `.env.local` configure principalement le frontend Next.js dans `apps/impress` ;
- `common.local` est chargé par les services Docker `app-dev`, `celery-dev` et le fournisseur de collaboration ;
- `common.local` surcharge les valeurs de développement définies dans `src/docs/env.d/development/common` sans modifier ce fichier partagé.

Créez ou modifiez le fichier suivant sur le serveur :

```bash
cd /chemin/vers/dinum-setup
touch src/docs/env.d/development/common.local
chmod 600 src/docs/env.d/development/common.local
```

Pour un serveur accessible à l'adresse `207.175.155.66`, les variables essentielles sont notamment :

```dotenv
# URL après connexion et URL de retour en cas d'échec
LOGIN_REDIRECT_URL=http://207.175.155.66:3000/
LOGIN_REDIRECT_URL_FAILURE=http://207.175.155.66:3000/
LOGOUT_REDIRECT_URL=http://207.175.155.66:3000/

# Hôtes autorisés pour les redirections OIDC
OIDC_REDIRECT_ALLOWED_HOSTS="207.175.155.66:3000,207.175.155.66:8071,207.175.155.66:8083"

# URLs OIDC accessibles depuis le navigateur et les services publics
OIDC_OP_JWKS_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/certs
OIDC_OP_AUTHORIZATION_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/auth
OIDC_OP_USER_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/userinfo
OIDC_OP_INTROSPECTION_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/token/introspect

# URL publique de collaboration et des médias
COLLABORATION_SERVER_ORIGIN=http://207.175.155.66:4444/
MEDIA_BASE_URL=http://207.175.155.66:8083/
```

Le endpoint de token peut rester interne au réseau Docker :

```dotenv
OIDC_OP_TOKEN_ENDPOINT=http://nginx:8083/realms/impress/protocol/openid-connect/token
```

Le backend réalise cet échange de token côté serveur ; le navigateur n'a pas besoin d'accéder directement à cette URL interne.

### Ne pas mettre les mots de passe dans la documentation

Les valeurs comme `OIDC_RP_CLIENT_SECRET`, `DJANGO_SECRET_KEY` et les mots de passe Keycloak doivent rester dans les fichiers locaux ou dans un gestionnaire de secrets. Ne les copiez jamais dans une page de documentation ni dans Git.

### Recharger la configuration

Après chaque modification de `common.local`, recréez les services qui utilisent ce fichier :

```bash
cd /chemin/vers/dinum-setup
make dev-docs
```

La cible `make dev-docs` appelle le `Makefile` du projet Docs et recrée les services de développement nécessaires. Si vous devez préparer le projet pour la première fois, utilisez plutôt :

```bash
make bootstrap-docs
```

> ⚠️ `make dev` lance plusieurs projets de La Suite. Pour travailler uniquement sur Docs, préférez `make dev-docs`.

La commande Compose reste utile uniquement pour vérifier la configuration, sans démarrer de service :

```bash
docker compose -f src/docs/compose.yml config >/dev/null
```

Vérifiez ensuite la configuration chargée :

```bash
docker compose -f src/docs/compose.yml config \
  | grep -E "LOGIN_REDIRECT_URL|OIDC_REDIRECT_ALLOWED_HOSTS|OIDC_OP_AUTHORIZATION_ENDPOINT"
```

Une ligne isolée sans `=` dans `common.local` provoque une erreur Docker du type `invalid environment variable: =...`. Le fichier doit contenir uniquement des lignes `NOM=VALEUR`, des commentaires et des lignes vides.

## 5. `kc_auth.local` : conserver Keycloak sur l'URL publique

Keycloak construit les URLs de son formulaire de connexion à partir de son hostname. Si ce hostname reste configuré sur `localhost`, la page peut commencer sur l'adresse publique puis rediriger le navigateur vers `localhost:8083`. Le cookie de session n'est alors plus retrouvé et Keycloak affiche : **« Restart login cookie not found »**.

Pour un accès depuis `207.175.155.66`, créez ou complétez :

```dotenv
# src/docs/env.d/development/kc_auth.local
KC_HOSTNAME=http://207.175.155.66:8083
KC_HOSTNAME_STRICT=false
```

Le fichier `kc_auth.local` est chargé par le service `keycloak` en complément de `kc_auth`. Il surcharge donc `KC_HOSTNAME=http://localhost:8083` défini dans le fichier commun.

Après modification :

```bash
make dev-docs
```

Cette commande recrée également Keycloak, Nginx et le backend via le `Makefile` du projet Docs. Pour contrôler explicitement les valeurs chargées sans afficher les secrets :

```bash
docker compose -f src/docs/compose.yml config \
  | grep -E "KC_HOSTNAME|LOGIN_REDIRECT_URL|OIDC_REDIRECT_ALLOWED_HOSTS|OIDC_OP_AUTHORIZATION_ENDPOINT"
```

Contrôle rapide : l'action du formulaire Keycloak doit commencer par :

```text
http://207.175.155.66:8083/realms/impress/login-actions/authenticate
```

Si l'ancienne URL `localhost` est encore ouverte dans le navigateur, supprimez les cookies de `localhost` et de `207.175.155.66`, puis relancez la connexion.

Les identifiants de démonstration du realm importé sont `impress / impress`. Le compte `admin / admin` sert à administrer Keycloak, pas à se connecter à Docs.

## 6. Frontend Docker : remplacer l'API `localhost`

Le service frontend de développement lit `.env.local`. Pour une image frontend de production ou le service `frontend` de `compose-e2e.yml`, l'URL de l'API est injectée par l'argument Docker `API_ORIGIN`. Cette valeur se configure depuis le setup : elle est transmise à Compose au moment du build et ne nécessite pas de modification directe dans le projet Docs.

> ⚠️ **Attention à `localhost` :** dans une application exécutée dans le navigateur, `localhost` désigne l'ordinateur de l'utilisateur. Sur un serveur distant, utilisez toujours l'IP ou le domaine accessible depuis le navigateur, par exemple `http://207.175.155.66:8071`.

Sur un serveur distant, utilisez l'URL accessible depuis le navigateur :

```bash
API_ORIGIN=http://207.175.155.66:8071 \
  docker compose -f src/docs/compose-e2e.yml build frontend
```

Les fichiers Compose du setup utilisent cette valeur avec un repli local :

```yaml
API_ORIGIN: "${API_ORIGIN:-http://localhost:8071}"
```

Si votre serveur utilise l'IP publique `207.175.155.66`, vous pouvez aussi exporter la variable avant toutes les commandes Compose de la session :

```bash
export API_ORIGIN=http://207.175.155.66:8071
docker compose -f src/docs/compose-e2e.yml build frontend
make -C src/docs run-e2e
```

> ⚠️ **Après une modification de `API_ORIGIN`, reconstruisez l'image frontend.** Une variable `NEXT_PUBLIC_*` est intégrée au build : redémarrer uniquement le conteneur ne suffit pas.

> ⚠️ **Ne mettez jamais `http://localhost:8071` dans une image destinée à être consultée depuis un autre ordinateur.** Le navigateur interpréterait `localhost` comme sa propre machine et les requêtes API échoueraient avec `ERR_CONNECTION_REFUSED`.

### Contrôle depuis le setup

Avant de lancer le build, vérifiez la valeur réellement transmise à Compose :

```bash
API_ORIGIN=http://207.175.155.66:8071 \
  docker compose -f src/docs/compose-e2e.yml config \
  | grep -A3 -B3 "API_ORIGIN"
```

Le résultat attendu contient `http://207.175.155.66:8071`, et non `http://localhost:8071`.

## 7. Procédure complète sur un serveur

### Étape 1 : Préparer le serveur

```bash
git clone git@github.com:suitenumerique/dinum-setup.git
cd dinum-setup

# Vérifier les versions disponibles
node --version
pnpm --version
docker compose version
```

### Étape 2 : Installer les dépendances de Docs

```bash
cd src/docs/src/frontend/apps/impress
pnpm install
```

### Étape 3 : Configurer `.env.local`

Créez le fichier local et renseignez les URLs correspondant à votre serveur :

```bash
cp .env.example .env.local
chmod 600 .env.local
```

Si le projet ne fournit pas de `.env.example`, créez `.env.local` manuellement à partir de la liste des variables utilisées dans le code et dans la documentation du projet Docs.

### Étape 4 : Vérifier `allowedDevOrigins`

Adaptez `src/docs/src/frontend/apps/impress/next.config.js` uniquement si vous lancez le serveur Next.js en mode développement depuis un domaine ou une IP différente.

### Étape 5 : Construire l'application

```bash
pnpm build
```

La configuration actuelle utilise `output: "export"` : la construction produit donc un site statique. Le déploiement doit servir le dossier de sortie avec un serveur web ou un reverse proxy configuré pour le domaine public.

### Étape 6 : Tester depuis le navigateur

Vérifiez successivement :

1. que le domaine résout vers le bon serveur ;
2. que HTTPS est actif si le domaine est public ;
3. que l'application s'affiche sans erreur réseau ;
4. que les appels vers l'API utilisent la bonne URL ;
5. que les ressources statiques et les routes avec slash final sont servies correctement.

## 8. Développement distant et production : ne pas confondre

`allowedDevOrigins` et `.env.local` ne suffisent pas à sécuriser un déploiement de production :

- **Développement distant :** Next.js écoute souvent sur une adresse accessible depuis le réseau et `allowedDevOrigins` limite les origines autorisées.
- **Production statique :** `pnpm build` génère les fichiers à servir ; le domaine et le TLS sont gérés par le serveur web ou le reverse proxy.
- **Variables d'environnement :** avec `output: "export"`, les variables `NEXT_PUBLIC_*` sont intégrées au build. Toute modification nécessite généralement un nouveau build.
- **Secrets :** ils doivent être fournis par le gestionnaire de secrets ou l'environnement du serveur, jamais par une valeur commitée dans le dépôt.

> ⚠️ **Production :** l'exemple avec `207.175.155.66` est adapté à ce serveur de démonstration. Pour une vraie mise en production, utilisez HTTPS et un nom de domaine stable, puis remplacez cette IP dans `common.local`, `kc_auth.local`, `allowedDevOrigins` et `API_ORIGIN`.

> ⚠️ **Authentification :** si Keycloak redirige vers `localhost:8083` ou affiche « Restart login cookie not found », vérifiez `kc_auth.local`, supprimez les anciens cookies du navigateur et recréez `keycloak`, `nginx` et `app-dev`.

> ⚠️ **Réseau :** `API_ORIGIN`, `LOGIN_REDIRECT_URL`, `KC_HOSTNAME` et `OIDC_REDIRECT_ALLOWED_HOSTS` doivent correspondre au même domaine ou à la même IP publique. Une seule valeur restée sur `localhost` peut casser la connexion.

## 9. Vérification finale

```bash
# Depuis src/docs/src/frontend/apps/impress
pnpm build

git status --short
git check-ignore -v .env.local
docker compose -f src/docs/compose.yml config >/dev/null
docker compose -f src/docs/compose.yml config | grep -E "KC_HOSTNAME|LOGIN_REDIRECT_URL|OIDC_REDIRECT_ALLOWED_HOSTS|OIDC_OP_AUTHORIZATION_ENDPOINT"
```

Le résultat attendu est :

- le build se termine sans erreur ;
- `.env.local` n'apparaît pas dans `git status` ;
- `git check-ignore` indique la règle qui ignore `.env.local` ;
- `KC_HOSTNAME` utilise l'adresse publique et non `localhost` ;
- les redirections OIDC utilisent `207.175.155.66:3000` et le callback API `207.175.155.66:8071` ;
- l'URL API injectée dans une image frontend distante n'est pas `localhost:8071` ;
- l'image frontend a été reconstruite après toute modification de `API_ORIGIN` ;
- le domaine public correspond à une entrée de `allowedDevOrigins` uniquement lorsque le serveur Next.js est lancé en développement.

## 10. Configuration complète prête à copier-coller

Cette procédure utilise le chemin réel du serveur : `/home/deploy/dinum-setup`. Elle crée uniquement les fichiers locaux de configuration ; elle ne modifie pas le code source du projet Docs.

> ⚠️ **Avant de commencer :** les fichiers `.local` et `.env.local` contiennent la configuration propre au serveur. Ne les commitez jamais. Les valeurs `CHANGE_ME_*` ci-dessous doivent être remplacées avant le démarrage.

### Étape 1 : se placer dans le setup et préparer les fichiers

```bash
cd /home/deploy/dinum-setup
make env-docs
```

### Étape 2 : créer `common.local`

Copiez ce bloc tel quel. Il configure les redirections publiques, OIDC, les médias et la collaboration pour `207.175.155.66` :

```bash
cat > /home/deploy/dinum-setup/src/docs/env.d/development/common.local <<'EOF'
# Clef Fernet Django : générer une vraie valeur avec src/docs/bin/fernetkey
OIDC_STORE_REFRESH_TOKEN_KEY=CHANGE_ME_GENERATE_FERNET_KEY

# URLs publiques accessibles depuis le navigateur
LOGIN_REDIRECT_URL=http://207.175.155.66:3000/
LOGIN_REDIRECT_URL_FAILURE=http://207.175.155.66:3000/
LOGOUT_REDIRECT_URL=http://207.175.155.66:3000/
OIDC_REDIRECT_ALLOWED_HOSTS="207.175.155.66:3000,207.175.155.66:8071,207.175.155.66:8083"
COLLABORATION_SERVER_ORIGIN=http://207.175.155.66:4444/
MEDIA_BASE_URL=http://207.175.155.66:8083/
IMPRESS_BASE_URL="http://207.175.155.66:8072/"

# Endpoints OIDC publics utilisés pour le parcours navigateur
OIDC_OP_JWKS_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/certs
OIDC_OP_AUTHORIZATION_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/auth
OIDC_OP_USER_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/userinfo
OIDC_OP_INTROSPECTION_ENDPOINT=http://207.175.155.66:8083/realms/impress/protocol/openid-connect/token/introspect
EOF

chmod 600 /home/deploy/dinum-setup/src/docs/env.d/development/common.local
```

> ⚠️ **Ne renseignez pas `OIDC_STORE_REFRESH_TOKEN_KEY` avec une valeur inventée.** Générez-la avec le script réellement présent dans le clone Docs :

```bash
cd /home/deploy/dinum-setup/src/docs
./bin/generate-oidc-store-refresh-token-key.sh
```

Le script ajoute la clé dans `env.d/development/common.local`. Si vous avez déjà créé le fichier avec le bloc ci-dessus, supprimez d'abord la ligne `OIDC_STORE_REFRESH_TOKEN_KEY=CHANGE_ME_GENERATE_FERNET_KEY`, puis exécutez le script.

### Étape 3 : créer `kc_auth.local`

Ce fichier empêche Keycloak de générer des URLs `localhost:8083` après la saisie du compte `impress` :

```bash
cat > /home/deploy/dinum-setup/src/docs/env.d/development/kc_auth.local <<'EOF'
KC_HOSTNAME=http://207.175.155.66:8083
KC_HOSTNAME_STRICT=false
EOF

chmod 600 /home/deploy/dinum-setup/src/docs/env.d/development/kc_auth.local
```

> ⚠️ Si Keycloak affiche **« Restart login cookie not found »**, supprimez les cookies de `localhost` et `207.175.155.66`, puis recréez les services avec `make dev-docs`.

### Étape 4 : créer le `.env.local` du frontend

Ce fichier est lu par Next.js dans l'application frontend :

```bash
cat > /home/deploy/dinum-setup/src/docs/src/frontend/apps/impress/.env.local <<'EOF'
NEXT_PUBLIC_API_ORIGIN=http://207.175.155.66:8071
NEXT_PUBLIC_PUBLISH_AS_MIT=false
NEXT_PUBLIC_SW_DEACTIVATED=true
EOF

chmod 600 /home/deploy/dinum-setup/src/docs/src/frontend/apps/impress/.env.local
```

> ⚠️ `NEXT_PUBLIC_API_ORIGIN` est exposée au navigateur. Elle ne doit contenir qu'une URL publique, jamais un mot de passe, une clé privée ou un token.

### Étape 5 : vérifier les fichiers sans afficher les secrets

```bash
cd /home/deploy/dinum-setup
test -s src/docs/env.d/development/common.local
test -s src/docs/env.d/development/kc_auth.local
test -s src/docs/src/frontend/apps/impress/.env.local
grep -q '^NEXT_PUBLIC_API_ORIGIN=http://207.175.155.66:8071$' \
  src/docs/src/frontend/apps/impress/.env.local
grep -q '^KC_HOSTNAME=http://207.175.155.66:8083$' \
  src/docs/env.d/development/kc_auth.local
docker compose -f src/docs/compose.yml config >/dev/null
echo "Configuration de fichiers valide"
```

> ⚠️ Ne faites pas `cat common.local` ou `docker compose config` sans filtre dans un terminal partagé : la sortie peut contenir des secrets.

### Étape 6 : démarrer Docs avec les commandes du setup

Pour une première installation :

```bash
cd /home/deploy/dinum-setup
make bootstrap-docs
```

Après une modification de `common.local`, `kc_auth.local` ou `.env.local` :

```bash
cd /home/deploy/dinum-setup
make dev-docs
```

Pour suivre le backend :

```bash
cd /home/deploy/dinum-setup
make logs-docs
```

### Étape 7 : vérifier le parcours de connexion

1. Ouvrir `http://207.175.155.66:3000/`.
2. Être redirigé vers `http://207.175.155.66:8083/` et non vers `localhost`.
3. Utiliser les identifiants de démonstration `impress / impress`.
4. Revenir sur `http://207.175.155.66:3000/`.
5. Vérifier que l'API répond depuis le navigateur :

```bash
curl -sS -o /dev/null -w "API config: HTTP %{http_code}\n" \
  http://207.175.155.66:8071/api/v1.0/config/
```

Le résultat attendu est `API config: HTTP 200`. Un `401` sur `/api/v1.0/users/me/` avant connexion est normal ; après connexion, la session doit être reconnue.

> ⚠️ Si une URL `localhost` apparaît encore, vérifiez dans cet ordre : `.env.local`, `common.local`, `kc_auth.local`, puis recréez les services avec `make dev-docs`. Ne relancez pas uniquement le frontend sans reconstruire lorsque `API_ORIGIN` a changé.
