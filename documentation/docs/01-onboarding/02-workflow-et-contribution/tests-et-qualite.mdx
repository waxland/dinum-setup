La fiabilité et la sécurité de **La Suite numérique** reposent sur une politique rigoureuse de tests automatisés (unitaires, intégration, bout-en-bout) et de vérification continue du style de code (_linting_).

🔗 **Frameworks de test & outils :** [Pytest Docs](https://docs.pytest.org/) • [Vitest Docs](https://vitest.dev/) • [Playwright E2E](https://playwright.dev/) • [Spécification Conventional Commits](https://www.conventionalcommits.org/fr/v1.0.0/)

## 🎯 1. Conventions Générales de Contribution

Avant de soumettre une Pull Request sur l'un des dépôts :

- 📝 **Conventional Commits** : Préfixez vos messages de commits selon la norme (`feat: ...`, `fix: ...`, `docs: ...`, `refactor: ...`, `test: ...`).
- 🧹 **Linting Propre** : Votre code ne doit produire aucune erreur ou avertissement de linter.
- ✅ **Tests Passants** : Toute nouvelle fonctionnalité ou correction de bug doit s'accompagner de ses tests automatisés.

## 🔬 2. Le Quality Gate Unifié (`make check`)

Dans le cadre du monorepo DINUM `/slash`, toutes les commandes de linting, typage et tests ont été unifiées à la racine pour garantir un standard de qualité homogène sur l'ensemble des paquets.

L'outil central de votre quotidien de développeur est la commande :

```bash
make check
```

Cette commande exécute séquentiellement **16 étapes de validation**, garantissant que le code respecte strictement les normes d'État (0 violation) :

1. **Formatage et Linting TypeScript :** `npm run format:check` et `npm run lint` (ESLint, Prettier).
2. **Typage Stricte TypeScript :** `npm run typecheck` (0 erreur `any` ou `as` silencieuse).
3. **Formatage et Linting Python :** `ruff format --check .` et `ruff check .` (Règles PEP8 et imports).
4. **Vérification Mypy :** Typage statique Python.
5. **Vérification des Dépendances :** `npm audit` pour bloquer les failles de sécurité connues.
6. **Tests Unitaires TypeScript :** `make packages-test-js` (Vitest sur le SDK et BlockNote).
7. **Tests Unitaires Python :** `make packages-test-python` (Pytest sur Django avec mocks DB/Redis).
8. **Tests Accessibilité / E2E :** `npm run test:e2e` (Playwright & Axe-Core).
9. **Build de la Documentation :** `npm run docs:build` (0 erreur SSR sur les portails Zudoku).

## ⚙️ 3. Commandes Ciblées par Écosystème

Si vous travaillez sur une brique spécifique et souhaitez accélérer la boucle de rétroaction sans lancer la vérification globale `make check`, voici les commandes ciblées à exécuter depuis la racine du workspace :

### A. Frontend (React / TypeScript)

```bash
# Formater tous les fichiers (JS, TS, MDX, JSON)
npm run format

# Lancer le linter ESLint en corrigeant automatiquement
npm run lint:fix

# Vérifier les types TypeScript sans transpiler
npm run typecheck

# Lancer les tests unitaires frontend (Vitest)
npm run test:js
```

### B. Backend (Python / Django)

```bash
# Lancer Ruff (linter) avec correction automatique
ruff check --fix .

# Formater le code Python avec Ruff
ruff format .

# Exécuter les tests unitaires backend (Pytest)
make packages-test-python
```

## 🚀 4. Intégration Continue (GitHub Actions)

Chaque Push ou Pull Request sur ce dépôt déclenche automatiquement une pipeline stricte sur GitHub Actions (`ci-packages.yml` et `ci-docs.yml`) reproduisant à l'identique l'environnement local :

1. **Matrice multi-OS** : Exécution sur `ubuntu-latest` et environnements isolés.
2. **Versionnage** : Tests sur Node.js 22 LTS et Python 3.12/3.13/3.14.
3. **Accessibilité** : Exécution stricte de `@axe-core/playwright` sur les composants interactifs.
4. **Sécurité** : Validation des overrides de dépendances (`tomlAndOverrides.test.ts`) empêchant l'inclusion accidentelle de packages vulnérables.

> 🛑 **Note sur les fusions** : Une Pull Request ne peut être fusionnée dans la branche principale `main` que si et seulement si l'ensemble des _Checks_ GitHub Actions sont au vert.
